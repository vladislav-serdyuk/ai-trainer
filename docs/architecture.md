# Архитектура AI-тренажёра

Документ описывает целевую архитектуру прототипа AI-тренажёра для абитуриента и
стажёра. Он рассчитан на разработчиков проекта: объясняет границы компонентов,
правила зависимостей и ключевые технические решения. Принятые решения
зафиксированы отдельно в [docs/adr/](adr/README.md).

## 1. Что делаем

Чат-бот, который ведёт живой диалог с пользователем в роли опытного наставника:
задаёт каверзные вопросы по слабым местам, разбирает ответ и даёт обратную связь
в трёх форматах — «Это верно», «Вот что можно улучшить», «Вот удачный пример
ответа». Основа ответов — база знаний, собранная из открытых источников.

Продукт выполняет обязательные этапы задания 1–3 (категория **Senior**).
Дополнительный этап 4 (кросс-сессионная адаптация и PDF-экспорт) в текущий объём
не входит, но архитектура оставляет для него точки расширения (см. §11).

Требования задания: [docs/task.md](task.md).

## 2. Ключевые ограничения

Эти ограничения определяют бо́льшую часть решений, поэтому вынесены в начало.

| Ограничение | Следствие для архитектуры |
|---|---|
| **GPU: RTX 4050 Laptop, 6 GB VRAM** | Нельзя одновременно держать в VRAM LLM + STT + эмбеддер/реранкер. Использование GPU **сериализуется**. |
| **Локальный инференс** | Модели работают на машине разработчика/демо, без внешних API по умолчанию. |
| **Python 3.12** | Гарантированные колёса для torch/vLLM/ctranslate2. См. [ADR-0007](adr/0007-python-3-12.md). |
| **Один пользователь на демо** | Достаточно Ollama; vLLM нужен только при переезде на серверную GPU. См. [ADR-0003](adr/0003-local-llm-ollama-then-vllm.md). |
| **Открытые источники** | База знаний собирается из открытых источников с указанием авторства; обязательна минимизация персональных данных. |

## 3. Общая схема пайплайна

```
                  ┌─────────────────────────────────────────────┐
 [текст] ─────────►                                              │
 [голос] ─► [STT] ─►        Оркестратор (pipeline)               │
                  │   FSM: сценарий → режим → шаг → feedback    │
                  │             │                               │
                  │             ▼                               │
                  │          Агент (LLM + tools)                │
                  │        ┌────┴───────────────┐               │
                  │        ▼                    ▼               │
                  │   tools: retriever      tools: web_search   │
                  │        │  (RAG, pgvector)   (duckduckgo)     │
                  │        ▼                    ▼               │
                  │   База знаний            Интернет           │
                  │        └──────────┬─────────┘               │
                  │                   ▼                         │
                  │        Структурированный ответ + цитаты      │
                  └───────────────────┬─────────────────────────┘
                                      ▼
                              [сообщение пользователю]
```

Данные диалога и результаты разбора сохраняются в PostgreSQL (см.
[docs/database.md](database.md)).

## 4. Слои и правила зависимостей

Проект делится на слои. **Правило: слой знает только о слоях ниже и никогда —
о слоях выше.** Это позволяет тестировать и заменять компоненты по отдельности
(например, подменить Ollama на vLLM без правок бизнес-логики).

```
bot           — транспорт (aiogram), FSM, клавиатуры, ввод/вывод
pipeline      — оркестрация: выбор сценария/режима, сборка контекста, вызов агента
agent         — LLM-клиент, инструменты (retriever, web_search), structured output
rag           — ingest KB, chunking, эмбеддинги, ретрив, реранк, цитаты
stt           — преобразование аудио в текст
repository    — доступ к БД (модели, миграции, запросы)
```

Зависимости направлены вниз: `bot → pipeline → agent → rag → repository`.
`agent` и `rag` не импортируют `bot`; `repository` не знает ни о чём выше.
`stt` — независимый лист, вызывается из `pipeline`.

## 5. Компоненты

### 5.1 Bot (`src/ai_trainer/bot/`)
Точка входа `main.py`, хендлеры aiogram, клавиатуры, FSM-хранилище. Отвечает
только за транспорт: принять текст/голос, показать меню, отдать результат.
Вся логика — в `pipeline`.

### 5.2 Pipeline / оркестратор (`pipeline/`)
«Мозг» бота. Управляет FSM-машиной диалога, выбирает сценарий и режим, собирает
контекст (история + известные ошибки текущей сессии), вызывает агента и
интерпретирует результат, сохраняет состояние и сообщения через `repository`.

Состояния FSM:

```
idle
 └─ choose_scenario
      └─ choose_mode
           ├─ informational : qa_loop  ──► answer_with_citations
           └─ trainer       : case_loop ──► evaluate_answer ──► feedback ──► summary
```

**Сессии.** Сессия — это один пользователь в одном сценарии и режиме от начала до
завершения (таблица `sessions`, см. [database.md](database.md#sessions)).

- **Источник истины.** Долгое состояние (сценарий, режим, прогресс, `case_index`)
  живёт в БД. aiogram-FSM хранит только эфемерное «жду ввод». После перезапуска
  бота или возврата пользователя сессия восстанавливается из БД.
- **Одна активная сессия на пользователя** — частичный уникальный индекс
  `unique(user_id) where ended_at is null`.
- **Сериализация по пользователю** — `asyncio.Lock` на `user_id`, чтобы два
  пришедших подряд сообщения обрабатывались по очереди.
- **Жизненный цикл:**
  1. `/start` → проверка согласия (`users.consent_at`); если нет — показ
     `legal_texts/` и ожидание подтверждения.
  2. Меню → выбор сценария → выбор режима → создание строки `sessions`.
  3. `informational`: цикл `qa_loop` — каждый запрос проходит retriever → агент →
     ответ с цитатами; сообщения пишутся в `messages`.
  4. `trainer`: на старте выбираются 3–5 кейсов (`case_ids`), затем цикл
     `case_loop`: `prompt` → ответ (голос → STT) → оценка → запись в
     `case_answers` + `messages` → обратная связь → `case_index++`.
  5. `summary`: агрегация вердиктов/ошибок по текущей сессии → завершение
     (`ended_at`).
- **Завершение** — по `/stop`, `/menu`, смене сценария/режима или по таймауту
  неактивности (`last_activity_at`). Установка `ended_at` освобождает активный
  слот.
- **Удаление данных** — `/delete` очищает сессии, сообщения и ответы пользователя
  (см. [ADR-0010](adr/0010-ethics-and-data-minimization.md)).

### 5.3 Agent (`agent/`)
Обёртка над LLM. Содержит:
- `LLMClient` — OpenAI-совместимый клиент (`openai` SDK), провайдер и модель
  задаются конфигом (`LLM_PROVIDER`, `LLM_BASE_URL`, `LLM_MODEL`).
- определение инструментов (function calling): `retriever` (RAG) и, опционально,
  `web_search`.
- сборку промптов и валидацию структурированного ответа.

Выбор провайдера — деталь конфигурации, а не кода. См.
[ADR-0003](adr/0003-local-llm-ollama-then-vllm.md) и
[ADR-0008](adr/0008-structured-llm-output.md).

### 5.4 RAG (`rag/`)
Двухконтурная база знаний:
- **Документы** — текстовые источники, разбитые на чанки, для информационного
  режима и заземления ответов. Каждый чанк связан с метаданными источника
  (URL, тип, дата обращения).
- **Структурированные кейсы** — вопросы тренажёра, эталонные ответы, типовые
  ошибки. Это не векторный поиск, а обычные записи БД (см. §8).

Ретрив: эмбеддинги (`multilingual-e5-small`) + pgvector (cosine), далее
опциональный реранк (`bge-reranker-v2-m3`). Ответ агента обязан ссылаться на
источники из KB.

### 5.5 STT (`stt/`)
`faster-whisper` (int8), русский язык. Аудио из Telegram (ogg/opus) конвертируется
в 16 kHz mono WAV через ffmpeg. По умолчанию модель работает на **CPU**, чтобы не
конкурировать за 6 GB VRAM с LLM. См. [ADR-0004](adr/0004-stt-faster-whisper-cpu.md).

### 5.6 Repository (`repository/`)
Асинхронный SQLAlchemy 2.x + Alembic. Модели и репозитории по сущностям,
инкапсулируют все SQL-запросы. Детали — [docs/database.md](database.md).

## 6. Управление VRAM (6 GB)

Поскольку все тяжёлые модели не помещаются в VRAM одновременно, действует
правило **сериализации**:

1. Голос → STT (CPU).
2. LLM (GPU) выполняет запрос и освобождает память между вызовами.
3. Эмбеддинги/реранк — CPU (приемлемо для коротких запросов и небольшой KB).

Профили моделей (`test` / `local` / `server`) позволяют гонять лёгкие модели
(например, Qwen2.5-1.5B) на этой машине и более крупные — на сервере, без правок
кода.

> **Переезд на GPU (расширение).** При достаточной VRAM STT и LLM смогут работать
> на GPU одновременно: `STT_DEVICE`/`STT_COMPUTE_TYPE` — конфиг, а не хардкод,
> поэтому переход сводится к смене переменных, установке CUDA/cuDNN и введению
> очереди на инференс STT (модель не потокобезопасна). Ориентир — 0.5–1 день,
> в основном ops. См. [ADR-0004](adr/0004-stt-faster-whisper-cpu.md#переезд-на-gpu-расширение).

## 7. Режимы работы

- **Информационный** — на запрос пользователя агент извлекает релевантные
  фрагменты KB и возвращает ответ со списком источников.
- **Тренажёр-экзаменатор** — по сценарию выдаётся 3–5 проблемных кейсов; ответ
  пользователя оценивается, формируется обратная связь в трёх форматах и ссылка
  на удачный пример/источник.

Сценарии и модель кейсов описаны в [docs/scenarios.md](scenarios.md).

## 8. Структурированный вывод LLM

Свободный текст не гарантирует формат обратной связи. Поэтому ответ агента —
это JSON, валидируемый через pydantic; при несоответствии схеме выполняется
ретрай, затем fallback-сообщение.

- Информационный режим:
  `{ "answer": str, "citations": [ { "document_id", "url", "title", "quote" } ] }`
- Режим тренажёра:
  `{ "verdict": "correct|partial|incorrect", "what_to_improve": str,
     "example_answer": str, "detected_mistakes": [id], "citations": [...] }`

Поля `what_to_improve` и `example_answer` напрямую реализуют форматы
«вот что можно улучшить» и «вот удачный пример ответа». См.
[ADR-0008](adr/0008-structured-llm-output.md).

## 9. Живой поиск (опционально)

`duckduckgo_search` подключается как инструмент `web_search` за интерфейсом
`SearchProvider`. Используется только как дополнение к RAG, всегда с цитированием,
и имеет fallback: при недоступности бот продолжает работать на базе знаний.
См. [ADR-0006](adr/0006-web-search-duckduckgo.md).

## 10. Данные, приватность и этика

- Бот всегда сообщает, что рекомендации носят информационный характер и не
  заменяют официальные требования вузов и работодателей.
- При первом запуске — согласие на основе `legal_texts/` (политика
  конфиденциальности, EULA). Команда `/delete` удаляет историю пользователя.
- Хранится минимум данных: `telegram_id` и история сессий; персональные данные
  без необходимости не собираются.
- В базе знаний указываются источники и лицензии.
- См. [ADR-0010](adr/0010-ethics-and-data-minimization.md).

## 11. Вне текущего объёма (Senior)

Этап 4 задания (адаптивное обучение по слабым зонам между сессиями и экспорт
диалога в PDF) **не реализуется**. Точки расширения заложены так, чтобы добавить
его без переработки:

- Результаты разбора уже сохраняются (`case_answers`), — на их основе можно
  считать профиль слабых зон.
- В `sessions`/`case_answers` есть ссылки на `mistake_catalog`, — агрегация по
  пользователю добавляется отдельным представлением/таблицей.
- Экспорт в PDF — отдельный сервис, читающий историю сессии.

## 12. Стек

Основные компоненты:
- Python 3.12
- aiogram (Telegram-бот)
- Ollama (позже vLLM) + Qwen2.5
- faster-whisper (STT)
- duckduckgo_search (веб-поиск)
- PostgreSQL + pgvector

Вспомогательные:
- SQLAlchemy 2.x (async), Alembic
- pydantic / pydantic-settings
- Docker, Docker Compose
- uv, ruff, mypy --strict, pre-commit, pytest

Обоснование выбора — в [docs/adr/](adr/README.md).

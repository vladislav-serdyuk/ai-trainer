# 0006. Веб-поиск через duckduckgo_search за абстракцией

- **Дата:** 2026-10-16
- **Статус:** Accepted
- **Контекст задачи:** этап 2 (информационный режим), живой поиск «желательно»

## Контекст

Информационный режим выигрывает от свежих данных из интернета. Для прототипа
нужен поиск без API-ключей и лишних договоров.

## Рассмотренные варианты

1. **duckduckgo_search** — без ключей, быстрый старт, подходит для прототипа;
   минусы: нестабильность выдачи и возможные лимиты.
2. Поисковые API (Google/Bing/SerpAPI) — стабильнее, но требуют ключей и денег.

## Решение

Мы используем поиск **duckduckgo_search** (с 2026-10-19 — его преемник
**`ddgs`**, переименование того же пакета) за интерфейсом `SearchProvider`.
Поиск — только **дополнение** к RAG, всегда с цитированием источника. При
недоступности сервиса бот продолжает работать на базе знаний (fallback), не
выдавая ошибок пользователю.

**Политика вызова (вариант B, 2026-10-19).** В информационном режиме решение о
поиске принимает **код, а не модель**: на каждый вопрос пользователя выполняется
запрос по его тексту параллельно с ретривом KB, результат кладётся в системный
контекст. Модель не вызывает инструмент `web_search` и не решает, искать ли.
Причина — маленькая локальная LLM (4B) ненадёжно вызывала инструмент и требовала
подпорок-эвристик; детерминированный вызов убирает эту нестабильность. Выдача
перед попаданием в контекст прошла стадии **clean** (дедуп по url без
трекинг-параметров, лимит 1 результат на домен) и **rerank** тем же
кросс-энкодером, что и KB; успешные результаты кэшируются на
`WEB_SEARCH_CACHE_TTL`. Сравнение вариантов (`raw` / `clean` / `rewrite+rerank`)
показало, что реранк повышает релевантность top-5 и долю официальных источников,
а переформулировка запроса моделью, наоборот, теряет ключевые сущности и вредит.

**Обогащение контекста (2026-10-20).** Снипет поисковика часто не содержит
нужного факта (курс, дата, условие). Поэтому для top-`WEB_SEARCH_PAGE_COUNT`
результатов (по умолчанию 3) параллельно скачивается сама страница: html
превращается в текст без внешних зависимостей и обрезается по лимиту символов
(`WEB_SEARCH_PAGE_FETCH`). Тексты страниц кэшируются по url на том же TTL, что и
выдачи; при таймауте/401/блокировке остаётся снипет. Это осознанный компромисс:
контекст становится фактологичнее, но загрузка добавляет задержку (до таймаута на
страницу, параллельно), а простой экстрактор тянет навигационный шум.

## Последствия

- Положительные: нет внешних зависимостей и ключей, изоляция за интерфейсом
  позволяет позже подключить платный провайдер; поведение поиска детерминировано
  и не зависит от капризов function calling у 4B.
- Отрицательные: нестабильность выдачи/лимиты — снижаем fallback'ом, кэшем и тем,
  что смысловой основой остаётся KB, а не поиск; поиск на каждый запрос добавляет
  задержку при промахе кэша и отправляет текст вопроса в DDG; догрузка страниц
  добавляет ещё до таймаута на страницу и обращается к внешним сайтам.
- Приватность: наружу уходят текст вопроса и запросы к найденным страницам;
  скачанный текст страниц в БД не сохраняется — живёт только в контексте хода и
  в TTL-кэше процесса (см. [ADR-0010](0010-ethics-and-data-minimization.md)).

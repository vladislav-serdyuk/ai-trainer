# 0009. Слоистая архитектура и правила зависимостей

- **Дата:** 2026-10-16
- **Статус:** Accepted
- **Контекст задачи:** проектирование, тестируемость, миграции

## Контекст

Проект объединяет транспорт (Telegram), оркестрацию диалога, LLM, RAG, STT и БД.
Без разграничения ответственности любой компонент начнёт зависеть от остальных, а
замена LLM или STT потребует правок во всём коде.

## Решение

Мы делим код на слои и задаём направление зависимостей **сверху вниз**:

```
bot → pipeline → agent → rag → repository
stt — независимый лист, вызывается из pipeline
```

Правило: **слой знает только о слоях ниже и никогда — о слоях выше.** Внешние
сервисы (Ollama/vLLM, Whisper, DuckDuckGo) скрыты за интерфейсами
(`LLMClient`, `SearchProvider`), поэтому заменяются конфигом.

## Последствия

- Положительные: юнит-тесты слоёв по отдельности с моками; дешёвая миграция
  провайдеров; понятная ответственность модулей.
- Отрицательные: чуть больше абстракций и boilerplate — оправдано для проекта
  такого размера. Риск «протекания» деталей: код ревью следит за тем, чтобы в
  `pipeline` не было, например, SQL.
